
# Сложный фильтр 
1. Выполнен запрос: SELECT * FROM receipt_item WHERE product_id = 25 AND purchase_price BETWEEN 100 AND 500. В таблицу receipt_item предварительно вставлен миллион строк случайных данных. Перед первым выполнением на таблице не было никаких дополнительных индексов, кроме первичного ключа по полю id.

2. Gather с двумя рабочими процессами, внутри каждого — Parallel Seq Scan на таблице receipt_item. Фактические временные показатели: общее время выполнения 39.250 мс, максимальное время среди параллельных процессов 36.215 мс, при этом каждый процесс отфильтровал в среднем 333367 строк, а всего строк возвращено 400. Буферы: shared hit=47, read=7309. План целиком: Gather (cost=1000.00..15691.21 rows=399 width=24) (actual time=0.190..39.225 rows=400 loops=1) -> Parallel Seq Scan (cost=0.00..14651.31 rows=166 width=24) (actual time=0.489..36.215 rows=133 loops=3) Filter: ((purchase_price >= '100'::numeric) AND (purchase_price <= '500'::numeric) AND (product_id = 25)) Rows Removed by Filter: 333367.

3. Полное последовательное сканирование всей таблицы (Seq Scan), несмотря на параллелизацию. Из миллиона строк условиям удовлетворяют только около 400, поэтому 99,96% данных отбрасываются фильтром, что приводит к огромным накладным расходам на чтение. Операции ввода-вывода: прочитано 7309 блоков с диска и 47 из кэша, то есть практически вся таблица. Время 39.250 мс для миллиона строк — при росте объёма данных время будет расти линейно.

4. Создать составной индекс по полям (product_id, purchase_price). Первое поле — точное сравнение, второе — диапазон. Такой индекс позволит выполнить Index Scan (или Bitmap Index Scan) и найти только те строки, где product_id = 25, а затем среди них быстро отобрать записи с purchase_price от 100 до 500, полностью избежав чтения всей таблицы.

5. CREATE INDEX idx_receipt_item_product_price ON receipt_item (product_id, purchase_price). Индекс построен по полям в указанном порядке, тип B-Tree (по умолчанию).

6. Bitmap Heap Scan на receipt_item с условием индекса, и внутри него Bitmap Index Scan на созданном индексе. Фактическое время выполнения сократилось до 2.651 мс. Детали плана: Bitmap Heap Scan (cost=13.51..1308.13 rows=399 width=24) (actual time=0.137..2.543 rows=400 loops=1) Recheck Cond: ((product_id = 25) AND (purchase_price >= '100'::numeric) AND (purchase_price <= '500'::numeric)) Heap Blocks: exact=388 Buffers: shared hit=13 read=379 -> Bitmap Index Scan on idx_receipt_item_product_price (cost=0.00..13.41 rows=399 width=0) (actual time=0.099..0.099 rows=400 loops=1) Index Cond: ((product_id = 25) AND (purchase_price >= '100'::numeric) AND (purchase_price <= '500'::numeric)) Buffers: shared read=4. Время планирования 0.249 мс.

7. Без индекса время выполнения 39.250 мс, с индексом — 2.651 мс, ускорение примерно в 14,8 раза. Количество прочитанных буферов сократилось с 7356 (47+7309) до 392 (13+379), то есть в 18,8 раза. Вместо параллельного последовательного сканирования всей таблицы теперь используется битовое сканирование индекса, которое обращается только к 388 блокам кучи (Heap Blocks) и 4 блокам индекса. Количество возвращённых строк совпадает (400), точность фильтрации достигнута без лишних операций.

8. Ггипотеза полностью подтверждена. Составной индекс (product_id, purchase_price) эффективно устранил узкое место полного сканирования таблицы. Он оптимален для запросов, содержащих условие равенства по первому столбцу и диапазон по второму. Рекомендуется создавать такие индексы для часто выполняемых аналитических запросов с комбинированными фильтрами.
