### Сложный фильтр

1. `SELECT * FROM receipt_item`
   `WHERE product_id = 25`
   `AND purchase_price BETWEEN 100 AND 500`

2. Gather с двумя рабочими процессами,
   внутри каждого – Parallel Seq Scan на таблице receipt_item.
   Фактические временные показатели:
   общее время выполнения 39.250 мс,
   максимальное время среди параллельных процессов 36.215 мс,
   при этом каждый процесс отфильтровал в среднем 333367 строк,
   а всего строк возвращено 400.
   Буферы: shared hit=47, read=7309.
   План целиком:
   `Gather (cost=1000.00..15691.21 rows=399 width=24)`
   `(actual time=0.190..39.225 rows=400 loops=1)`
   `-> Parallel Seq Scan (cost=0.00..14651.31 rows=166 width=24)`
   `(actual time=0.489..36.215 rows=133 loops=3)`
   `Filter: ((purchase_price >= '100'::numeric)`
   `AND (purchase_price <= '500'::numeric)`
   `AND (product_id = 25))`
   `Rows Removed by Filter: 333367`

3. Полное последовательное сканирование всей таблицы (Seq Scan),
   несмотря на параллелизацию.
   Из миллиона строк условиям удовлетворяют только около 400,
   поэтому 99,96% данных отбрасываются фильтром,
   что приводит к огромным накладным расходам на чтение.
   Операции ввода-вывода: прочитано 7309 блоков с диска и 47 из кэша,
   то есть практически вся таблица.
   Время 39.250 мс для миллиона строк,
   при росте объёма данных время будет расти линейно.

4. Создать составной индекс по полям `(product_id, purchase_price)`.
   Первое поле – точное сравнение, второе – диапазон.
   Такой индекс позволит выполнить Index Scan (или Bitmap Index Scan)
   и найти только те строки, где `product_id = 25`,
   а затем среди них быстро отобрать записи
   с `purchase_price` от 100 до 500,
   полностью избежав чтения всей таблицы.
   B-дерево выбрано, потому что оно наилучшим образом поддерживает
   оба типа условий, присутствующих в запросе:
   точное сравнение по полю `product_id` и диапазон по полю `purchase_price`.
   B-дерево хранит данные в отсортированном виде,
   что позволяет после нахождения первой записи с `product_id = 25`
   продолжить последовательное чтение только тех записей,
   у которых `purchase_price` попадает в интервал от 100 до 500.
   При этом сложность поиска составляет O(log N) для нахождения начальной точки,
   а затем чтение результата линейно пропорционально
   количеству выбранных строк, а не размеру всей таблицы.
   Альтернативные типы индексов не подходят.
   Хеш-индекс поддерживает только сравнение на равенство, но не диапазоны.
   GIN-индекс предназначен для полнотекстового поиска
   и работы с массивами или JSONB, он избыточен и неэффективен
   для числового диапазона.
   GiST-индекс мог бы работать для диапазонов,
   но для простых чисел B-дерево быстрее и компактнее.
   BRIN-индекс подходит для очень больших таблиц,
   где значения физически коррелированы с порядком строк,
   но наш запрос требует точечного поиска по конкретному `product_id` –
   такой индекс пришлось бы сканировать полностью или почти полностью.
   B-дерево же обеспечивает надёжную производительность
   для комбинации равенства и интервала.

5. `CREATE INDEX idx_receipt_item_product_price`
   `ON receipt_item (product_id, purchase_price)`

6. Bitmap Heap Scan на receipt_item с условием индекса,
   и внутри него Bitmap Index Scan на созданном индексе.
   Фактическое время выполнения сократилось до 2.651 мс.
   Детали плана:
   `Bitmap Heap Scan (cost=13.51..1308.13 rows=399 width=24)`
   `(actual time=0.137..2.543 rows=400 loops=1)`
   `Recheck Cond: ((product_id = 25)`
   `AND (purchase_price >= '100'::numeric)`
   `AND (purchase_price <= '500'::numeric))`
   `Heap Blocks: exact=388`
   `Buffers: shared hit=13 read=379`
   `-> Bitmap Index Scan on idx_receipt_item_product_price`
   `(cost=0.00..13.41 rows=399 width=0)`
   `(actual time=0.099..0.099 rows=400 loops=1)`
   `Index Cond: ((product_id = 25)`
   `AND (purchase_price >= '100'::numeric)`
   `AND (purchase_price <= '500'::numeric))`
   `Buffers: shared read=4`
   Время планирования 0.249 мс.

7. Без индекса время выполнения 39.250 мс,
   с индексом – 2.651 мс,
   ускорение примерно в 14,8 раза.
   Количество прочитанных буферов сократилось с 7356 (47+7309)
   до 392 (13+379), то есть в 18,8 раза.
   Вместо параллельного последовательного сканирования всей таблицы
   теперь используется битовое сканирование индекса,
   которое обращается только к 388 блокам кучи (Heap Blocks)
   и 4 блокам индекса.
   Количество возвращённых строк совпадает (400),
   точность фильтрации достигнута без лишних операций.

8. Гипотеза полностью подтверждена.
   Составной индекс `(product_id, purchase_price)`
   эффективно устранил узкое место полного сканирования таблицы.
   Он оптимален для запросов, содержащих условие равенства
   по первому столбцу и диапазон по второму.
   Рекомендуется создавать такие индексы
   для часто выполняемых аналитических запросов
   с комбинированными фильтрами.

### Сортировка с ограничением (ORDER BY + LIMIT)

1. `SELECT * FROM receipt_item ORDER BY purchase_price DESC LIMIT 10`

2. План без индекса:
   `Limit (cost=21533.29..21534.46 rows=10 width=24)`
   `(actual time=180.797..182.095 rows=10 loops=1)`
   `  Buffers: shared hit=654 read=6774`
   `  -> Gather Merge (cost=21533.29..118810.92 rows=833750 width=24)`
   `      (actual time=180.795..182.092 rows=10 loops=1)`
   `        Workers Planned: 2, Workers Launched: 2`
   `        Buffers: shared hit=654 read=6774`
   `        -> Sort (cost=20533.27..21575.46 rows=416875 width=24)`
   `            (actual time=177.449..177.450 rows=8 loops=3)`
   `              Sort Key: purchase_price DESC`
   `              Sort Method: top-N heapsort Memory: 26kB`
   `              Buffers: shared hit=654 read=6774`
   `              -> Parallel Seq Scan on receipt_item`
   `                  (cost=0.00..11524.75 rows=416875 width=24)`
   `                  (actual time=0.091..146.573 rows=333500 loops=3)`
   `                    Buffers: shared hit=582 read=6774`
   `Planning Time: 0.082 ms`
   `Execution Time: 182.110 ms`

3. Полное последовательное сканирование всей таблицы (1 000 000 строк)
   с параллельной обработкой, затем сортировка всех строк по purchase_price DESC.
   Для получения всего 10 строк пришлось обработать миллион записей.
   Сортировка методом top-N heapsort выполняется в памяти,
   но требует чтения всех строк каждым воркером (~333 500 строк на воркер).
   Время выполнения 182.1 мс, из них 146.6 мс – сканирование,
   остальное – сортировка и слияние.
   Операции ввода-вывода: 654 блока из кэша и 6774 с диска – практически вся таблица.

4. Создать индекс на поле purchase_price (по убыванию).
   Индекс B-дерево поддерживает сортировку,
   поэтому запрос с ORDER BY purchase_price DESC LIMIT 10
   может выполнить Index Scan в обратном порядке,
   взяв первые 10 записей из индекса без чтения всей таблицы.
   Так как индекс содержит отсортированные значения,
   PostgreSQL сможет прочитать только первые 10 записей индекса,
   а затем для каждой из них обратиться к таблице.
   Сложность станет O(log N + k), где k = 10,
   что кардинально быстрее текущего плана.
   B-дерево выбрано, потому что оно хранит данные в отсортированном порядке
   и поддерживает как возрастающую, так и убывающую сортировку.
   Альтернативы (хеш, GIN, GiST) не подходят,
   так как не обеспечивают упорядоченный вывод.

5. Создан индекс:
   `CREATE INDEX idx_receipt_item_price_desc`
   `ON receipt_item (purchase_price DESC)`

6. Повторное выполнение запроса с индексом:
   `Limit (cost=0.42..0.98 rows=10 width=24)`
   `(actual time=0.050..0.118 rows=10 loops=1)`
   `  Buffers: shared hit=2 read=11`
   `  -> Index Scan using idx_receipt_item_price_desc on receipt_item`
   `      (cost=0.42..55419.92 rows=1000500 width=24)`
   `      (actual time=0.049..0.115 rows=10 loops=1)`
   `        Buffers: shared hit=2 read=11`
   `Planning Time: 0.204 ms`
   `Execution Time: 0.131 ms`

7. Без индекса время выполнения 182.110 мс,
   с индексом – 0.131 мс,
   ускорение примерно в 1390 раз.
   Количество прочитанных буферов сократилось с 7428 (654+6774)
   до 13 (2+11), то есть в 571 раз.
   Вместо параллельного последовательного сканирования всей таблицы
   и сортировки миллиона строк теперь выполняется Index Scan,
   который считывает только 10 записей из индекса
   и делает соответствующее количество обращений к таблице.
   Количество возвращённых строк совпадает (10).

8. Гипотеза полностью подтверждена.
   Индекс на поле сортировки (особенно с указанием направления DESC)
   радикально ускоряет запросы с ORDER BY и LIMIT.
   Без индекса база данных вынуждена сканировать и сортировать все строки,
   что приводит к огромным накладным расходам.
   Для запросов, которые часто извлекают «топ N» записей,
   индекс на соответствующем поле обязателен.

3. Полное последовательное сканирование всей таблицы (1 000 100 строк). Условие `lower(name) LIKE '%мультиварка%'` с ведущим `%` не может использовать обычный B‑Tree индекс.
Несмотря на крайне низкую селективность (всего 10 подходящих строк из миллиона), читаются все строки с диска. 
Время выполнения – **106,9 мс**, прочитано 8092 блока с диска (плюс 96 из кэша). Таким образом, при росте данных время будет расти линейно.

4. Для ускорения поиска произвольной подстроки в PostgreSQL используется расширение `pg_trgm`, позволяющее строить индексы на основе триграмм:
- GIN (Generalized Inverted Index) – инвертированный список триграмм, быстрый поиск.
- GiST (Generalized Search Tree) – сбалансированное дерево триграмм.

Гипотеза:
Оба индекса должны радикально ускорить запрос, поскольку позволят найти 10 строк без сканирования всей таблицы. Ожидается, что GIN будет быстрее GiST из‑за оптимизации под чтение.

5.
`
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX idx_product_name_gin ON product USING GIN (lower(name) gin_trgm_ops);
CREATE INDEX idx_product_name_gist_l ON product USING GiST (lower(name) gist_trgm_ops);
`

- GiST-индекс тоже эффективен, но его производительность оказалась на порядок хуже, что объясняется разной внутренней организацией: GIN хранит инвертированный список и быстрее находит редкие триграммы, тогда как GiST обходит дерево с бóльшими накладными расходами.


### Полнотекстовый поиск

1.`SELECT * FROM product WHERE name LIKE '%1035';`

Запрос ищет товары, название которых заканчивается на «1035» (например, «Мультиварка 1035», «Вода 1035», «Ноутбук 1035»). В таблице `product` 1 000 100 строк. Фактически условию удовлетворяют 100-150 записей.

2.
`

  Workers Planned: 2
  Workers Launched: 2
  Buffers: shared hit=100 read=8087
  ->  Parallel Seq Scan on product  (cost=0.00..13395.91 rows=42 width=34) (actual time=2.607..127.317 rows=38 loops=3)
        Filter: ((name)::text ~~ '%1035'::text)
        Rows Removed by Filter: 333332
        Buffers: shared hit=100 read=8087
Planning Time: 0.295 ms
Execution Time: 134.144 ms
`

3. 
Выполняется полное последовательное сканирование всей таблицы product, содержащей 1 000 100 строк, 
поскольку условие `LIKE '%1035'` с ведущим символом `%` не позволяет использовать обычный B‑Tree индекс. 
Несмотря на то, что подстроке «1035» удовлетворяют только 114 строк (селективность около 0,011%), 
сканированию подвергаются абсолютно все записи таблицы. Время выполнения такого сканирования составляет 134,1 мс, 
при этом с диска читается 8087 блоков данных плюс ещё 100 блоков из кэша. По мере увеличения объёма хранимых данных время выполнения будет расти линейно, 
что делает такой способ доступа неприемлемым для больших таблиц.

4.
Для ускорения поиска по суффиксу (и произвольной подстроке) используется расширение `pg_trgm` с GIN-индексом. Триграммы позволяют индексу эффективно находить строки, заканчивающиеся на заданную последовательность символов.

Гипотеза:  
После создания GIN-индекса на столбце `name` запрос будет использовать `Bitmap Index Scan`, найдёт записи по триграммам суффикса «1035» и прочитает только соответствующие блоки таблицы. Время выполнения должно сократиться в десятки/сотни раз.

`
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX idx_product_name_trgm ON product USING GIN (name gin_trgm_ops);
`

  Heap Blocks: exact=114
  Buffers: shared hit=18 read=110
  ->  Bitmap Index Scan on idx_product_name_trgm  (cost=0.00..52.75 rows=100 width=0) (actual time=0.390..0.391 rows=114 loops=1)
        Index Cond: ((name)::text ~~ '%1035'::text)
        Buffers: shared hit=14
Planning Time: 0.789 ms
Execution Time: 1.739 ms
`

- Количество операций ввода‑вывода уменьшилось с 8187 блоков до 142 (в 57,7 раз).

8. Гипотеза полностью подтверждена.
GIN-индекс с триграммами (`pg_trgm`) эффективно ускоряет поиск по суффиксу (`LIKE '%...'`). При селективности 0,011% ускорение составило 77 раз, а объём прочитанных данных сократился почти в 60 раз. Для регулярного поиска по окончаниям строк (например, артикулов, идентификаторов) данный индекс является оптимальным решением. В отличие от поиска по редкому слову (ускорение в тысячи раз), здесь возвращается больше строк (114), поэтому эффект меньше, но всё равно весьма значительный.

### Соединение таблиц (JOIN)

1. `SELECT ri.id, ri.quantity, ri.purchase_price, p.name, p.unit
FROM (
    SELECT id, quantity, purchase_price, product_id
    FROM receipt_item
    ORDER BY purchase_price DESC
    LIMIT 1000
) ri
JOIN product p ON ri.product_id = p.id
WHERE p.category_id = 3
ORDER BY ri.purchase_price DESC
LIMIT 100;`

2. План выполнения без индекса на receipt_item.purchase_price:

`Limit (cost=29617.41..37337.19 rows=5 width=496) (actual time=76.438..77.778 rows=100 loops=1)
Buffers: shared hit=1702 read=7258

4. Для ускорения операции ORDER BY purchase_price DESC LIMIT N необходимо создать B‑tree индекс по полю purchase_price в убывающем порядке. B‑tree хранит данные в отсортированной структуре, поэтому PostgreSQL может выполнить Index Scan в обратном порядке, последовательно считывая только первые N записей индекса и обращаясь к таблице только для этих строк. Это полностью исключает полное сканирование и сортировку. Индекс на (purchase_price DESC) выбран потому, что направление сортировки в запросе – DESC, а B‑tree позволяет эффективно читать как в прямом, так и в обратном порядке, но явное указание DESC может дать небольшое преимущество. Альтернативы (хеш, GIN) не поддерживают сортировку.

### Негативный сценарий: индекс не используется / не даёт прироста

1. `SELECT * FROM receipt_item WHERE purchase_price % 100 = 0;`

Условие: остаток от деления purchase_price на 100 равен нулю. Такое условие не является sargable (не может использовать обычный B‑tree индекс), так как применяет функцию к столбцу.

2. `Gather  (cost=1000.00..13668.83 rows=3935 width=48) (actual time=3.935..69.236 rows=71 loops=1)
  Workers Planned: 2
  Workers Launched: 2

3. Условие purchase_price % 100 = 0 не может использовать индекс, так как требует вычисления функции для каждого значения. Даже при наличии B‑tree индекса на purchase_price PostgreSQL не сможет применить его, потому что сравнение идёт не со столбцом, а с результатом арифметической операции. В результате выполняется полное сканирование таблицы (Parallel Seq Scan), при котором прочитано 6396 блоков с диска и 960 из кэша, а из миллиона строк условию удовлетворяют только 71 строка. Время выполнения ~69 мс.

4. Гипотеза: создание обычного B‑tree индекса на поле purchase_price не ускорит данный запрос, поскольку условие содержит арифметическую операцию над столбцом, что делает предикат не sargable. Планировщик PostgreSQL не сможет использовать такой индекс для фильтрации, так как индекс хранит значения purchase_price, а условие требует вычисления остатка от деления. Следовательно, запрос в любом случае будет выполнять полное сканирование таблицы. Индекс будет проигнорирован, и его создание лишь добавит накладные расходы на обслуживание без выигрыша в производительности.

5. `CREATE INDEX idx_receipt_item_purchase_price ON receipt_item (purchase_price);`

Ускорение отсутствует (фактически незначительное колебание в пределах погрешности). Индекс не используется, план остался тем же – параллельное последовательное сканирование. 8. Гипотеза подтвердилась: обычный B‑tree индекс на поле purchase_price действительно не ускорил запрос, поскольку условие WHERE содержит арифметическую операцию над столбцом и не является sargable. Для оптимизации такого запроса необходимо использовать функциональный индекс: CREATE INDEX ON receipt_item ((purchase_price % 100)); либо переписать условие, выделив остаток в отдельный вычисляемый столбец. Негативный сценарий демонстрирует, что даже при наличии индекса он может быть бесполезен, если предикат не позволяет выполнить индексный поиск.
